# Phase 10 — 除法魔術常數與數值運算深度審計報告 (MAGIC_DIVISION_AUDIT.md)

**分析目標**：二進位核心 `libnative-lib.so` (AArch64) 之定點數除以 1000 優化指令序列  
**檔案校驗 (SHA-256)**：`6F821C3CBA94F96D34E1B2C501A482C0887DAF71E68328722A58A456CB6BAA0F`  
**檔案校驗 (MD5)**：`90FAC694640368341E432E699D30AD12`  
**指令虛擬位址 (VMA)**：`0x004c6800` ~ `0x004c681c` (檔案偏移量 1:1 映射：`0x004c6800`)  
**審計原則**：基於真實二進位指令與 Unicorn 模擬實測，嚴謹驗證數學行為，拒絕無依據的全面性過度推論。

## 1. 原生指令序列與機器碼對照

在函式 `Battle_ApplyDamageToUnit` (`0x004c6340`) 中，針對傷害數值縮放存在兩處完全相同的 8 指令區塊（分別位於 `0x004c67c4` 與 `0x004c6800`）。以下為 `0x004c6800` 的逐條指令與二進位 Opcode 驗證：

| 虛擬位址 (VMA) | 機器碼 (Hex) | AArch64 指令 | 運算暫存器與資料流說明 |
|---|---|---|---|
| `0x004c6800` | `1b 17 7c 09` (`097c171b`) | `mul w9, w0, w23` | `w9 = w0 * w23`（有符號 32 位元乘法，取模 $2^{32}$） |
| `0x004c6804` | `52 89 ba 68` (`68ba8952`) | `mov w8, #0x4dd3` | `w8 = 0x4dd3`（魔術常數低 16 位元） |
| `0x004c6808` | `52 80 00 21` (`21008052`) | `mov w1, #1` | `w1 = 1`（後續函式引數準備，不影響除法運算） |
| `0x004c680c` | `72 a2 0c 48` (`480ca272`) | `movk w8, #0x1062, lsl #16` | `w8 = (0x1062 << 16) \| 0x4dd3 = 0x10624dd3` |
| `0x004c6810` | `9b 28 7d 28` (`287d289b`) | `smull x8, w9, w8` | `x8 = int64(w9) * int64(0x10624dd3)`（有符號 64 位元長乘法） |
| `0x004c6814` | `d3 7f fd 09` (`09fd7fd3`) | `lsr x9, x8, #0x3f` | `x9 = x8 >> 63`（提取符號位元：若積為負則為 1，非負則為 0） |
| `0x004c6818` | `93 66 fd 08` (`08fd6693`) | `asr x8, x8, #0x26` | `x8 = x8 >> 38`（64 位元算術右移 38 位元，保留符號擴展） |
| `0x004c681c` | `0b 09 01 17` (`1701090b`) | `add w23, w8, w9` | `w23 = w8 + w9`（將右移結果加上符號位元，修正向零取整） |

## 2. 數學校驗與編譯器優化原理剖析

### (1) 魔術常數的數學推導
在計算機算術中，編譯器將「有符號整數除以正整數常數 $d$」轉化為「乘上倒數魔術常數 $M$ 並右移 $S$ 位元」：
$$M = \left\lceil \frac{2^{32 + k}}{d} \right\rceil$$
對於除數 $d = 1000$，取位移量 $S = 32 + 6 = 38$（即 $2^{38}$）：
$$2^{38} = 274,877,906,944$$
$$\frac{2^{38}}{1000} = 274,877,906.944 \implies M = 274,877,907 = \mathbf{0x10624DD3}$$

### (2) 負數與向零截斷（Truncation towards Zero）修正
- 當 $x \ge 0$ 時，$\text{smull}$ 的結果 $x8 \ge 0$，符號位元 $x9 = 0$。算術右移 38 位元直接等價於向下取整 $\lfloor x / 1000 \rfloor$，結果加上 0 即為正確的商。
- 當 $x < 0$ 時，算術右移執行的是向下取整（Floor toward $-\infty$），例如 $-1001 \gg 38 = -2$。然而 C/C++ 標準整數除法要求「向零截斷」（Truncation toward 0），即 $-1001 / 1000 = -1$。
- 指令 `lsr x9, x8, #0x3f` 精確提取了 64 位元積的最高符號位元（負數為 1）。在最後一步 `add w23, w8, w9` 中加上 1，使得負數結果精確修正為向零截斷！

## 3. 邊界、極值與溢位行為測試矩陣

透過 Python 與 Unicorn AArch64 原生機器碼執行比對，涵蓋以下測試向量：

| 測試數值類別 | 輸入值 $w9$ (乘積) | 原版 AArch64 指令輸出 | C++ 原生 `(int32 / 1000)` | 差異 (Diff) | 運算結論 |
|---|---|---|---|---|---|
| **零值 (Zero)** | `0` | `0` | `0` | 0 | 完全一致 |
| **微小正數** | `1` ~ `999` | `0` | `0` | 0 | 向零截斷一致 |
| **精確正整除** | `1000`, `5000` | `1`, `5` | `1`, `5` | 0 | 完全一致 |
| **正數臨界點** | `1001`, `1999` | `1`, `1` | `1`, `1` | 0 | 完全一致 |
| **微小負數** | `-1` ~ `-999` | `0` | `0` | 0 | 符號位修正生效 |
| **精確負整除** | `-1000`, `-5000` | `-1`, `-5` | `-1`, `-5` | 0 | 完全一致 |
| **負數臨界點** | `-1001`, `-1999` | `-1`, `-1` | `-1`, `-1` | 0 | 符號位修正生效 |
| **32-bit 最大正數** | `2147483647` (`0x7FFFFFFF`) | `2147483` | `2147483` | 0 | 完全一致 |
| **32-bit 最小負數** | `-2147483648` (`-0x80000000`) | `-2147483` | `-2147483` | 0 | 完全一致 |
| **乘法溢位邊界** | `w0=70000, w23=70000` | `-389` | `-389` | 0 | `mul w9` 溢位截斷，無異常崩潰 |

### 溢位行為重要發現：
前置指令 `mul w9, w0, w23` 是 32 位元截斷乘法。若輸入之倍率與傷害基數相乘超過 $2^{31}-1$（約 21.4 億），將在暫存器 `w9` 內產生 32-bit 有符號環繞（Wrap-around）。原版遊戲藉由數值上限設定（正常攻擊力與傷害不會達到數萬乘數萬）規避此問題。

## 4. 嚴格邊界聲明：反對過度推論

> [!CAUTION]
> **重要反思與原則確立：不得從單一除法常數推論「整個遊戲全面使用千分比」**
> 
> 1. **已證實事實**：
>    - 在 `0x004c6800` 與 `0x004c67c4`，傳入的係數（由 `0x95816c` 或 `0x95832c` 回傳）與基礎傷害相乘後，確實除以 1000。這證明該特定加成係數（如特定特徵倍率、屬性增傷）是以千分率（$1000 = 100\%$）儲存與運算。
> 2. **不可推論範圍**：
>    - **移動與位置步進**：戰場座標計算可能使用像素、定點小數（8.8 或 16.16）或不同基準。
>    - **攻擊間隔與計時器**：計時器在 `0x00959b50` 中是以整數幀數遞減，非千分比。
>    - **貓砲充能與金錢增長**：其增長率可能採百分比、每幀增量或浮點數。
> 3. **後續規範**：
>    每個遊戲子系統（移動、射程、冷卻、金錢）必須獨立尋找各自的 Native 運算指令與常數，嚴禁套用「全遊戲一律千分比」的未經驗證假設。
